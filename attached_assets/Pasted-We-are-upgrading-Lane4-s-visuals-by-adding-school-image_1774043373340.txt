We are upgrading Lane4’s visuals by adding school images and styling the cards/deep dives so the product feels premium, warm, and real.

IMPORTANT
This is a visual/UI upgrade only.
Do NOT change:
- search logic
- admissions logic
- swim/recruiting logic
- deep dive narrative logic
- scoring labels
- school ranking behavior

GOAL
Implement a fast, automatic school image system with polished UI presentation.

We want:
1. ONE strong image on every school card
2. THREE images on every deep dive:
   - hero campus image (THE main campus shot)
   - student life image (kids on campus / campus vibe)
   - swim image (pool, team, aquatic center, swim culture)
3. a noticeably more premium visual feel across the app

==================================================
PART 1 — IMAGE STRATEGY
==================================================

We are starting with the fastest scalable approach.

For every school, dynamically generate or store image URLs using search-style queries. The goal is to get attractive images immediately for all schools without manual curation.

Preferred image categories per school:

A) Card / Deep Dive Hero Image
Query:
"{school name} campus"

B) Deep Dive Student Life Image
Query:
"{school name} students campus"

C) Deep Dive Swim Image
Query:
"{school name} swim team"
fallback:
"{school name} swimming pool"
fallback:
"{school name} aquatic center"

If possible, implement this through a simple helper that builds image URLs from search-based sources.

You may use a lightweight public image approach such as:
- Unsplash source-style query URLs
- Wikimedia Commons if convenient
- another simple public image mechanism that does NOT require us to manually populate hundreds of images right now

If using query-based image URLs, URL-encode school names properly.

We want the system to be easy to replace later with curated school-specific image URLs.

==================================================
PART 2 — DATA MODEL / HELPER
==================================================

Implement one of these two patterns, whichever is cleaner in our current codebase:

OPTION A — dynamic generation only
Create a helper like:

get_school_images(school_name)

Returns:
{
  "hero": ...,
  "student_life": ...,
  "swim": ...
}

OPTION B — enrich school data records at runtime
Add fields:
- image_hero_url
- image_student_life_url
- image_swim_url

If easier, keep these generated at runtime instead of permanently stored.

Either way:
- centralize the logic in one helper
- keep it easy to swap sources later
- use sane fallbacks

==================================================
PART 3 — FALLBACK RULES
==================================================

If a query-based image fails or looks broken:
1. retry with a simpler query:
   "{school name}"
2. for swim:
   retry with:
   "{school name} athletics"
3. if still unavailable:
   use a polished default placeholder image

We should have:
- one default campus placeholder
- one default student-life placeholder
- one default swim placeholder

Do NOT let broken image icons appear in the UI.
